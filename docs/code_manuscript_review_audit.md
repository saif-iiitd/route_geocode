# Code–manuscript–review fidelity audit

Audit date: 12 September 2026. Scope: `The_Geocoder.ipynb`, `routes_batch1_highlighted.xlsx`, `Revised Identifiable Manuscript July 2026.docx`, and `Reviews_March2026.docx`.

The notebook implements a rule-dispatched geocoder with independent first-result place resolution, selected waypoint operations, generic network routing, and synthetic fallback routes. It does **not** implement several safeguards described in the manuscript: confidence-based candidate selection, universal bounded snapping with required-role rejection, named-road clipping, or the documented Nominatim fallback and confidence-bearing output schema. These differences affect the claimed contribution, not merely implementation presentation.

This is an audit only. No source file was edited, no geocoding or routing service was called, and the notebook was not run as a pipeline. Only this Markdown report was created. Recommendations below are proposed future work, not completed fixes.

## Evidence conventions and limits

- **C<number>** means the notebook's one-based physical cell number, including Markdown cells. Function names identify the relevant code within the cell. Execution counts are separately identified where important.
- **M P<number>** means a one-based top-level paragraph in the manuscript, including empty paragraphs in the count. **M T<number>** identifies its tables: T1 ontology, T2 query operations, T3 configuration counts, T4 centralities, T5 spatial information scores.
- **R1.x / R2.x** refer to the reviewers' actual numbered comments. The response inserted after R1.4 and the revision-priority table in the review document are author/revision material, not additional reviewer comments.
- Spreadsheet references use the `routes_batch1` sheet. Columns A–F are annotation ID, original text, gold coordinates, system coordinates, gold GeoJSON, and system GeoJSON. Rows 2–51 contain 50 cases. Rows 54–56 are the highlight legend, not validation cases.
- Findings about code are established by inspection and small in-memory probes of extracted pure functions. Associations between a code defect and an individual validation failure are **hypotheses unless explicitly stated otherwise**. The workbook has no execution trace, selected candidates, role records, translated input, configuration, fallback status, API versions, or notebook revision identifier. It cannot establish the generating branch or service response for a case.
- Both DOCX files were read as text and tables; their document XML contains no tracked insertions/deletions or text boxes. This audit does not evaluate document layout or the visual accuracy of embedded manuscript figures.
- The manuscript refers to preprocessing, mapping and external datasets that are outside this four-file implementation boundary. Absence here means “not implemented or demonstrated in the supplied notebook,” not that no other implementation could exist.

## Actual implementation trace

1. **Tweet input.** C42 reads `Data/tweets_data.csv`, processes `translated_text` for the first 5,144 rows, and accepts four tweet bounding-box values. Translation itself is absent. Tokens excluding punctuation/space are printed, but routing/classification still receives the original input string. NLTK POS tags and dependency-based preposition lists are printed rather than used to construct a unified semantic representation. `is_removed` is calculated but unused.
2. **Entity recognition.** C10 loads `en_core_web_sm`, builds exact phrase `LOC` EntityRuler patterns from `Data/tweet_location_terms.txt`, and saves a model. C12 adds case-insensitive phrase matches with `PhraseMatcher(attr='LOWER')`, combines them with existing NER entities, and filters overlapping spans. C42 accepts LOC, GPE, ORG and FAC entities. There is no statistical fine-tuning loop, alias-to-canonical-place mapping, or separate gazetteer confirmation of every extracted span. The separately created `ruler` has `overwrite_ents=True`, but the pipeline ruler is created through a separate `nlp.add_pipe` call without that setting.
3. **Spatial classification.** C15 applies ordered regex searches directly to the complete tweet. The first matching category wins: **9, 8, 10, 11, 12, 7, 4, 3, 2, 1, 5, 6**, otherwise 0. No entity counts, POS tags, dependency attachments or graph checks enter this classifier. C15 classifies the loaded corpus before routing; inside C42 the dispatcher classification occurs after initial entity geocoding.
4. **Semantic roles.** Separate handlers re-run `nlp_tweet` and use suffix-string membership or entity counters to obtain roles. They do not construct or persist one common `(O,D,A,L)` record. C30 and C32 define the same `extract_origin_destination` name with incompatible scalar/list destination contracts. Some parsers preserve the first role, others overwrite roles as the token loop progresses. `starting at` is compared against single token text and is not handled as a bigram by these role parsers.
5. **Gazetteer lookup.** C42 calls `geocoder.geocode(point, proximity=delhi_center)` independently for each recognized entity. Most handlers repeat independent calls for their selected role names. Queries do not append city/country or supply explicit API bounds/country filters. Most candidate loops accept the first returned coordinate in latitude 28.4041–28.8832 and longitude 76.8377–77.6789. C18's P handler directly accepts `loc_info[0]` without this bounds test.
6. **Candidate selection.** No code reads confidence, compares candidate context, jointly resolves mentions, checks candidate route consistency, or records alternatives. Service response order determines the first acceptable result. Failed initial geocodes are omitted from `point_coords`, while `point_locations` remains intact.
7. **Road resolution.** C22/C36/C38 define `extract_line_road`; the final definition is C38. It downloads a Delhi drivable graph and selects edges with **`edges['name'] == road_name`**. There is no case/alias normalization, list-valued-name handling, reference/alternate-name search, or road relation resolver. A unary union is converted into one flat coordinate list, losing component boundaries and graph order.
8. **Route construction.** P returns a singleton coordinate list. MP routes all unordered pairs and concatenates their coordinates. L obtains named-road geometry only when there is one recognized entity; otherwise it calls ORS between successive surviving coordinates. ML also routes successive coordinates rather than unioning separate named roads. O/D sample four random points inside a geocoder bounding box and route outward/inward. O2D uses one ORS query. O2MD makes origin-to-destination queries and concatenates them, subject to the parser collision. O2D@P uses an ORS waypoint when all three roles resolve. O2DonL picks existing road vertices nearest to the endpoints, then runs a length-weighted shortest path over the **whole Delhi graph**. PonL chooses farthest road vertices with a broad opposite-bearing condition and routes on the whole graph through the nearest node to the point. P&D routes directly from the named point to the named directional target.
9. **Fallback.** If a handler returns an empty result, C42 connects all surviving geocoded points in mention order. With fewer usable points it re-geocodes entities and routes between southwest/northeast geocoder bounding-box corners; if no usable box is obtained, it uses the input tweet's bounding-box corners. Later entity iterations can overwrite an earlier fallback route. No direct Nominatim fallback is implemented. No entities causes an early skip; selected API failures cause skips; several handler failures can instead propagate uncaught exceptions.
10. **Output.** C42 filters coordinates, guesses axis order using `route_coordinates[0][0] > 50`, and converts only the returned display coordinates. It stores the **unconverted** `str(route_coordinates)` in `df` and writes `Data/routes_data.csv` on each successful row. There is no final Point/LineString construction, GeoJSON export, route-component schema, confidence computation, or enforced success/partial/fallback distinction. The workbook independently contains LineString GeoJSON, but its conversion code is not supplied.

## Validation evidence

### Coverage and interpretation

There are **50 annotation records**, **34 with gold and system coordinate pairs**, **15 with system output but no gold**, and **one with neither** (A002, row 3). All 34 gold coordinate values and all 49 system coordinate values have matching corresponding GeoJSON coordinate arrays. All 83 nonempty GeoJSON cells encode a single LineString. The notebook does not supply the transformation that produced those workbook GeoJSON values.

The legend is A54 “Very little overlap,” A55 “Exact match,” and A56 “Significant overlap.” Highlights are qualitative labels, not numerical evaluation results. For example, A029 is highlighted “Exact match” although its length and endpoints differ from gold. A068 is highlighted “Significant overlap” but has no gold geometry in this workbook. Missing gold must not be counted as failure or success.

The following independently calculated diagnostics characterize the supplied polylines. They are **approximate audit measurements, not publication-ready route accuracy scores**. Coordinates were mapped to a local plane using x = longitude × 111195 × cos(28.6°), y = latitude × 111195, in metres. Length is the sum of consecutive segment lengths. For buffered coverage, each segment was sampled at midpoints of subdivisions no longer than 40 m; its length contribution was counted when its sample lay within 100 m of any segment of the other line. `S100` is the share of system length near gold and `G100` the share of gold length near system. These are length-weighted, direction-insensitive diagnostics; they do not establish road identity, correct carriageway, continuity, or semantic roles. Repeated segments count repeatedly. Final evaluation should use an appropriate projected CRS, directed road/path metrics and prespecified tolerance sensitivity.

## Specific fidelity conclusions

### Confidence is neither candidate scoring nor route scoring here

There is no local confidence/context ranking, no joint entity resolution, no low-confidence trigger, and no saved candidate list. The code relies on whatever order OpenCage returns, then uses the first coordinate passing the local region test. This is weaker than M P71's explicit confidence-based selection. M P144 acknowledges absence of **per-route** confidence, which is distinct from candidate confidence; Appendix A nevertheless promises stored confidence and a `compute_confidence` function that does not exist.

### Role failure is not proven to cause a direct index swap

The initial coordinate list loses entries when a geocode fails. However, the audited code does not zip that compressed list back to all original names to label origin/destination/landmark. Several handlers re-geocode role names directly. The demonstrated hazards are loss of required roles in generic fallback, counter-based role misassignment independent of geocode success, duplicate-name/span ambiguity, and incompatible parser return types. For example, with names `[origin, destination, landmark]` and an unresolved destination, the surviving-coordinate fallback can route origin → landmark without marking the destination missing. It must not be described as a successfully resolved intended route.

### Named-road endpoints are not a named-road constraint

C36 moves endpoints to nearby vertices of an exact-name road match and then routes on the unrestricted graph. That can coincidentally follow the named road, but no operation requires it. There is no clipping to the named road between projected endpoints. C38 similarly uses full-graph paths for PonL. Nearest-node calls exist, but the promised common bounded snapping stage and required-role rejection do not.

### Flattening exists before LineString conversion

The notebook demonstrably concatenates coordinates from distinct routes and road components. It does **not** itself instantiate the final single LineString. The workbook does contain single-LineString exports, with no component boundaries. It is therefore sound to flag the flattening and resulting risk of artificial connectors, but not to invent an absent notebook export function or attribute every long workbook route to flattening. Long examples such as A052 may also contain actual detours/retraversal; its largest adjacent step is approximately 699 m, not a demonstrated single 70 km connector.

### Historical outputs do not resolve reproducibility

An isolated in-memory probe with recognized names Alpha/Beta gives `('Alpha', 'Beta')` after C30 and `('Alpha', ['Beta'])` after C32. The saved execution counts reverse which definition is active compared with top-to-bottom execution. In the saved-order state, O2MD can iterate a scalar destination string character by character. In a fresh top-to-bottom state, O2D can pass a destination list into a geocoding call. The service/library response to that malformed contract was not tested.

C42's saved output also contains an explicit generic-fallback message after a P&D alert mentioning AIIMS and R.K. Puram, demonstrating that fallback is not merely dead code. Those outputs are not a verified trace for the workbook's A-cases. C15's saved category counts agree with M T3, supporting category-count fidelity without establishing route fidelity.

### Absent or overstated implementation details

The supplied notebook does not implement the claimed statistical NER fine-tuning, mandatory BBBike entity verification, city/country query composition, IN API filtering, confidence threshold/ranking, per-role GeoDataFrame provenance, direct Nominatim fallback, a universal 200 m snapping policy, named-road clipping, a route candidate probability model, exhaustive feasible O/D routing, final multipart/typed geometry handling, or the advertised GeoJSON/confidence export. Some appendix statements conflict with the main text: “exclude infeasible” versus “ensure complete coverage,” and absence of confidence versus confidence-bearing outputs. These must be reconciled with the final verified implementation before resubmission.
